# Interview Q&A: modular monolith module boundaries

Companion to [ADR-001](0001-modular-monolith-module-boundaries.md). Ten interviewer-style questions on the boundary-enforcement work, with the reasoning behind each answer.

---

**1. What is a modular monolith, and why choose it here instead of microservices or a plain, unstructured monolith?**

A modular monolith is a single deployable unit that's internally decomposed into modules by business capability — each module owns its own package tree, its own persistence, and talks to other modules through an explicit API rather than reaching into their internals. It sits between two failure modes: a "big ball of mud" monolith, where nothing stops modules from coupling to each other's internals over time, and a microservices split, which buys independent deployability at the cost of network calls, distributed transactions, and multi-repo operational overhead. For a codebase where the domain boundaries aren't fully proven yet, a modular monolith lets you get the *design* benefit of clear seams — so a future extraction to services is a mechanical move, not a rewrite — without paying the distributed-systems tax on day one.

**2. The compiler doesn't stop one module from importing another module's classes in a monolith. How do you actually enforce a boundary that "doesn't really exist" at the JVM level?**

You enforce it with an architecture test that runs in CI, not with the compiler. We use Spring Modulith's `ApplicationModules.verify()`, which statically analyzes the compiled types and fails the build if a module reaches into another module's `internal` package or if there's a package cycle across modules. On top of that we added two custom ArchUnit rules for coupling patterns Modulith's own check doesn't model. The common thread is: boundaries that only live in documentation or code review erode under pressure; boundaries that fail the build don't.

**3. Walk me through how Spring Modulith decides what counts as a "module."**

Modulith treats each top-level package directly under the application's base package (the package `@SpringBootApplication` lives in — `com.example.relay` here) as a module. Within a module, anything under an `internal` sub-package is considered private to that module; everything else is that module's public API. `ApplicationModules.verify()` then checks that no module has a Java-level dependency on another module's `internal` types, and that there's no cyclic dependency between modules. Our custom rule (`ArchitectureRules.moduleOf`) uses the same convention — the package segment immediately after the base package — so the two layers of checking agree on what a "module" is.

**4. You already had `ApplicationModules.verify()` from an earlier ticket. Why add custom ArchUnit rules on top of it — isn't that redundant?**

They check different things. `verify()` operates purely at the Java package/type level: it stops one module's code from calling into another module's internal classes. It has no concept of JPA or the database. Our two rules close gaps that are specific to a persistence-heavy monolith: `noCrossModuleEntityImports` flags a class in one module holding a direct reference to another module's `@Entity`, which is exactly how modules end up sharing a data model even if they're otherwise well isolated. `noCrossSchemaJoins` flags a JPA relationship annotation (`@ManyToOne`, `@OneToMany`, etc.) that spans two different `@Table(schema = ...)` values — something Hibernate will happily generate a join for, and something `verify()` has no visibility into at all, since it's a mapping-metadata concern, not a Java-dependency concern. So it's not redundant — it's three layers, each catching a different way the boundary can be violated.

**5. Why specifically ban importing another module's `@Entity`, rather than just relying on the `internal` package convention to hide it?**

Two reasons. First, defense in depth: if an entity is ever accidentally placed outside `internal` (or the Modulith check is misconfigured), we still want a clear, second signal specifically about entity coupling before it turns into a shared data model. Second, the failure message matters. A generic "illegal dependency" error from Modulith tells you *that* something's wrong; our rule's message — "module X must not depend on an entity in module Y ... reference the other module's aggregate by id instead" — tells you the *fix*. That's a deliberate design choice: rules that name a corrective action get fixed faster than rules that just say "no."

**6. Explain the cross-schema join rule in your own words. What real bug does it prevent?**

Each module is meant to own its own database schema — that's our unit of data ownership, mirroring the module boundary in the code. The rule walks every `@Entity`'s relationship fields (`@OneToOne`, `@OneToMany`, `@ManyToOne`, `@ManyToMany`, and defensively `@JoinColumn`/`@JoinTable`), resolves what entity type each one targets — including unwrapping collection types like `List<OrderLine>` via ArchUnit's generic-type model — and checks that the target's `@Table(schema = ...)` matches the source's. If they differ, it fails. The bug this catches: two modules can have perfectly separate Flyway-migrated schemas, and application code can still map a `@ManyToOne` from one module's entity straight into the other's, at which point Hibernate silently generates a cross-schema join. That's real coupling — a schema change in module B now breaks module A's query — and it's invisible to both Modulith's `verify()` and to a casual read of the migration files, since the migrations themselves stay clean.

**7. Say module A legitimately needs data owned by module B — an order needs to know a product's current price. How do you do that without violating the rule?**

You don't hold a JPA reference to the other module's entity at all. The two sanctioned options are: (a) module A stores the other module's aggregate id as a plain value (a `UUID productId` field, not a `@ManyToOne Product`) and calls module B's public API — a service method or, per Modulith's event support, an application event — when it needs current data; or (b) if you need it inline in a query, you denormalize the specific field you need at write time rather than joining live. Both keep the schemas independent and keep the coupling explicit and one-directional through a real API, instead of implicit through the object graph.

**8. These are architecture rules about code, tested with more code. How did you actually validate that the ArchUnit rules themselves are correct?**

By building minimal fixture packages before pointing the rule at real code: `archunitfixtures.nocrossmoduleentityimports` and `archunitfixtures.nocrossschemajoins`, each with a `clean` variant (should pass) and a `violating` variant (should fail) — e.g. a `catalog.internal.domain.Product` and an `ordering.internal.domain.Order` in different schemas, with the violating version giving `Order` a `@ManyToOne` straight to `Product`. `NoCrossModuleEntityImportsRuleTest` and `NoCrossSchemaJoinsRuleTest` run the rule against both variants and assert pass/fail. That gives confidence in the rule's logic in isolation, decoupled from whatever the real codebase happens to look like on a given day. Only after that does `ModuleBoundaryArchitectureTest` point the same rule at `com.example.relay` for real, with `allowEmptyShould(true)` so it doesn't fail vacuously before any real modules or entities exist.

**9. The module-detection logic is "the package segment right after the base package." What are the failure modes of that heuristic?**

The main risk is a false negative: any package that sits at that same level but isn't a real bounded-context module — a shared `common` or `util` package, for instance — gets treated as its own "module," so code in one real module depending on a class in `common` wouldn't be flagged even if `common` were later given an `@Entity` of its own by mistake. It also assumes module identity never needs anything more specific than the top-level package name — it wouldn't handle, say, two independently-versioned sub-modules nested under one top-level package. Given the codebase has no real modules yet, this hasn't bitten us, but it's the first thing I'd revisit once `ordering`/`catalog`-style packages actually exist: probably by explicitly listing module packages rather than inferring them positionally, or excluding known shared packages from the check.

**10. If a PM later asked you to peel one of these modules out into its own microservice, what does this boundary-enforcement work actually buy you?**

The extraction becomes mechanical instead of exploratory. Because no module ever held a direct reference to another module's `@Entity` and no JPA relationship ever crossed a schema boundary, the module's data is already isolated to its own schema with no live joins to unwind — you can lift that schema into its own database as-is. Because inter-module communication already goes through an explicit API/event boundary rather than shared objects, extracting the module means turning that in-process call into a network call (REST, messaging, whatever fits), not rewriting the module's internals to discover what it was actually coupled to. In other words: the ArchUnit rules mean we'd find out about hidden coupling *now*, at build time, for free — instead of finding out during a service extraction, the expensive way.
